## 0. 一句话结论

我们比竞品多走了一步的地方只有两处，且都是**机制约束**而非话术：**规则参数的版本治理（草稿 / 已发布 / 已退役 + 发布前案例门禁）**，以及**发现（Finding）必须引用证据定位、全部改动留痕**。头部厂商把"可解释、可追溯"当卖点讲，但公开资料里看不到同等的机制约束。反过来，**审查立场 × 审查尺度**其实是全行业标配——立场我们刚做完，**尺度（严格 / 中立 / 宽松）仍缺且补起来接近零成本**。收官阶段的增量应压在机制优势的**演示**与**尺度补齐**上，而不是再铺功能面。

## 2. 机制对拼：我们已做深、竞品普遍没做到的两条

### 2.1 规则参数版本化 + 发布前案例验证

**我们的实现**（`apps/api/src/db/schema.ts` `ruleVersions`、`apps/api/src/db/rule-repository.ts`）：

- 每个规则版本有明确状态 **`draft` / `published` / `retired`**，一个规则至多一个草稿；**已发布版本不可变**，审计快照引用它，因此历史决策永远能回溯到当时那套参数。
- 参数修改只能新建草稿；**草稿必须跑过金标准案例集且通过，才能发布**（`rule-repository.ts` 的发布门禁：没有待发布草稿、尚未运行验证、验证未通过、没有可验证案例，分别以 409 拒绝）。评测执行路径 `packages/audit/src/golden-eval.ts` 与 `bun test` 基准共用，门禁不会与测试口径漂移。
- 快照把"哪条规则用了哪个已发布版本"记进评估（`model.ts` 的 `ruleVersion` / `ruleVersionId`），Finding 继承这个编号，**一次决策可被追到确切参数集**。

**竞品面**：头部的电子签/合同云厂商普遍有"模板库、条款库、审批流"，但公开资料里**看不到把规则参数本身做成带状态、带发布门禁的版本对象**，也看不到"发布前必须过一批带期望结果的案例"这一步。e签宝、华宇元典等在文案里强调"可解释、可追溯"，但从公开面看，那是**事后说明能力**，而不是**事前约束机制**——没有"没过验证就发不出去"的硬闸门。

**结论**：这是我们最硬的一条差异，且是评委能当场验证的机制（新增草稿→跑验证→失败被拒→修正→通过→发布）。演示价值高于再加规则数量。

### 2.2 Finding 强制引用证据定位 + 全留痕

**我们的实现**：

- 证据锚定不可变原件：`DocumentSpanLocator`（`packages/audit/src/model.ts`）带 `contractDocumentHash`、`blockId`、`startOffset`、`endOffset`、`quotedText`，即"哪份原件、哪个块、第几个字符到第几个字符"。
- 提案守卫 `packages/audit/src/proposal-guard.ts` 用**规则契约表**约束可提交的发现类型与严重程度：制度冲突时严重程度由规则**锁定**，需人工复核时只能在区间内取值；对不合规、不适用、无对应违规维度的提交一律报错。也就是说，Agent **不能**凭一句"我觉得有风险"落一条发现。
- 复核决策只追加，每次决策生成新的 Finding Revision，历史不可覆盖。

**竞品面**：几乎所有玩家都会演示"点击风险点跳到原文"。但公开资料里**很少展示"没有证据定位就提交不了发现"这类拒绝路径**，也没有把"参数版本 + 评估 + 证据 + 复核决策"串成一条只追加链路的说明。点得到原文 ≠ 结构上引用证据。

**结论**：这是第二硬的差异。演示时应主动展示**被拒绝的提交**，让机制可见。

## 3. 审查立场 × 审查尺度

### 3.1 全行业标配

成熟产品的审查都不是"一套规则打天下"，而是让用户选**立场**（我是甲还是乙）与**尺度**（严还是松）：

- **立场**：同一份合同，买方与卖方的风险方向相反。竞品普遍以"选择己方角色"或"上传时指明我是哪一方"的方式实现。
- **尺度**：严格 / 中立 / 宽松三档，或"审批阈值"式滑块，用来适配不同风险偏好的客户。

### 3.2 我们的现状

- **立场**：**已实现**。`packages/audit/src/contract-stance.ts` 有 `ContractStance = "revenue" | "procurement"`，能从当事人表的角色标签推断，并带 `basis`（判断依据）与 `decidedByPartyId`，让复核员可以不同意；规则按立场分档（`RULE_STANCE_APPLICABILITY`），不适用的规则会被过滤并说明原因。
- **尺度**：**仍缺**。目前只有制度阈值（如预付款上限比例 `limitRatio`）这一条松紧旋钮，没有面向用户的"严格 / 中立 / 宽松"档位。

### 3.3 补齐成本极低

因为规则参数已经版本化（§2.1），尺度本质上就是**三套预设参数**：

- 尺度 × 规则 = 一份草稿级的参数集（严格档收紧阈值，宽松档放宽），复用现有草稿→验证→发布链路即可，不需要改规则代码。
- 界面只需在审查发起处加一个三选一，把选中的预设写进快照，历史决策照样可回溯。

**建议**：把"尺度"作为收官阶段的低成本增量优先项——它补齐的是一个全行业标配缺口，而边际工作量接近零。

## 4. 带修订痕迹的 docx 回写

审查结论最终要回到 Word 里给法务改，最自然的形态是**带修订痕迹（tracked changes）的 docx**。技术选型判断：

| 方案 | 语言 | 能否产出真修订痕迹 | 备注 |
| --- | --- | --- | --- |
| `docx-revisions` | Python | ✅ `w:ins` / `w:del` | 可生成真修订稿 |
| `docx-redline-js` | JavaScript | ✅ `w:ins` / `w:del` | 与 Node/Bun 技术栈同源，首选 |
| `docxtemplater` | JS | ❌ | **不支持 `w:ins` / `w:del`**，只能做**批注版**（`w:comment`），无法让修改以"接受/拒绝修订"的形式呈现 |

**关键约束**：`docxtemplater` 在本项目语境下**不能**用于修订回写——它替换的是文本内容，不会写出修订标记；用它产出"修订稿"只会得到一份看不出改动的成品。若只需要批注提示，它可以胜任；若要"法务在 Word 里逐条接受/拒绝"，必须用前两者之一。

**建议**：JS 栈优先 `docx-redline-js`，与现有 Bun/TS 工程同源，省一层跨语言进程；`docx-revisions` 作为功能更强或格式更复杂时的备选。

## 5. 插件形态取舍（WPS vs Office.js）

如果审查能力要以插件形态落到用户桌面，两条路差异极大：

### 5.1 WPS 加载项（推荐路径）

- **内网唯一能全链路不出内网的路径**：WPS 在国内政企/内网办公环境普及，加载项可本地部署，无需把合同发往外部云。
- **修订 API 原生完整**：`TrackRevisions` 开关、`Revisions.Json()` 返回每条修订并**带 begin/end 位置**、可按条 `Accept` / `Reject`。这正好匹配"生成修订稿 → 法务逐条处理"的流程。
- **部署**：走 `wpsjs publish`。
- **红线**：**不要用 `jsplugins.xml`**——自 **12.1.0.16910** 起该配置方式已被官方限制，继续沿用会在新版本上失效。

### 5.2 Office.js（不推荐用于修订回写）

- **没有粒度化的 tracked-change diff API**：无法像 WPS 那样按条操作修订。用整段 `replace` 生成修改，Word 会记成"整段删除 + 整段插入"，**产出一份丑陋且不可读的修订稿**。
- **修订 API 仅限桌面端**：Web 版与移动端拿不到同样的能力，形态受限。

**结论**：面向内网政企场景，WPS 加载项是唯一能"全链路不出内网 + 真修订痕迹"的形态；Office.js 只在纯云、非修订场景才值得考虑。

## 6. 验证数据集修正

### 6.1 CUAD 不合适（原计划修正）

**CUAD**（Contract Understanding Atticus Dataset）在此前设想中被当作验证集，但它**不适合**验证我们的能力：

- **英文、美国法域**：我们的规则全是中文合同、中国法域（如违约金比例、管辖偏好），语言与法域双重不匹配。
- **并购尽调视角**：其标注体系服务于 M&A due diligence 的条款抽取，**无法验证我们的数值阈值规则**（预付款比例、付款期限、保证金比例这些带数字的判定，CUAD 根本不标）。

结论：**放弃用 CUAD 验证阈值类规则**，它验证不了我们要证明的东西。

### 6.2 更契合的替代：ProvBench / ProvData

**ProvBench / ProvData**（ACL 2025）是公开论文所述的数据集，特征与本项目高度对齐：

- **3550 条中文合同条款**、**24850 条标注**、覆盖 **8 类合同**——中文、多合同类型，适合做规则级验证。
- **附带 663 条法条库**：可直接给规则**挂法律依据**，让每条判定不只说"超阈值"，还能引用具体法条，天然契合"可解释、可追溯"的对外叙事。

> 口径说明：以上数量与构成来自该论文的公开描述，我们**未**在本地复现统计数据；引用时应随文标注来源与年份。

**建议**：把验证数据集口径从 CUAD 切换到 ProvBench/ProvData，并在演示中突出"法条库挂依据"这一点。

## 7. 对外口径纪律

**必须遵守的引用纪律**：凡是引用 **LawGeex** 那组"AI 审查准确率"数字，**必须同时注明三件事**——

- 口径是 **F-measure**（不是准确率/accuracy 的字面含义）；
- 数据年份是 **2018**；
- 样本仅是 **5 份 NDA**（保密协议），不代表复杂商业合同。

去掉任一限定，就等于把一个窄口径实验数字说成通用能力，经不起专业质询。

**建议改用更抗质疑的结论**：**ContractEval（2025）** 的评估结论是——**多数大模型的表现大致相当于初级法务助理水平**。这个说法：

- 年份新、来源可查；
- 结论保守，反而更容易被专业人士接受；
- 与我们"AI 提效但不替代人"的产品定位一致（我们本来就把最终决策留给人工复核）。

**一句话口径**：不提"我们比人准"，改提"我们把人从逐条核对里解放出来，判断仍归人类"。

## 8. 跨条款一致性：公认弱项，也是我们最难被复制的地方

**ACE / COMPACT（EACL 2026）** 的研究显示：即便是 SOTA 模型，**跨条款多跳推理的准确率也只有 34–57%**。也就是说，"把第八条的管辖和第十二条的争议解决放在一起看"这种活儿，纯模型能力当前就是短板。

> 口径说明：34–57% 为该论文报告的区间，随任务/模型而异；我们未在本地复现，引用须带论文出处与年份。

**为什么这是我们的机会**：我们的路径不是"让模型一口气读完全文再作答"，而是 **Agent + 受控工具多次读证据**——用确定性规则先把数值类判断做掉，再由 Agent 带着工具去跨条款取证，每条结论都落在具体字符区间上。这种"多次、可核对的读证据"正好补上单次推理在多跳上的短板，而且**难以被简单复制**：抄一个 prompt 容易，抄一整套证据锚定 + 规则门禁 + 留痕链路难。

**建议**：演示时专门设计一个跨条款案例（如收入/支出合同的付款条件与管辖背靠背），把"34–57%"与我们的逐条证据定位并排展示。

## 9. 已无需再做的一条（避免后续 agent 重做）

此前曾建议：**"把证据定位升级为带字符偏移的三元组"**。**该建议已不再需要**——证据定位器**本来就带字符偏移**。

`DocumentSpanLocator`（`packages/audit/src/model.ts`）的字段为：

```ts
{
  kind: "DOCUMENT_SPAN",
  contractDocumentHash: string,
  blockId: string,
  startOffset: number,   // ← 已有
  endOffset: number,     // ← 已有
  quotedText: string,
}
```

实测输出示例：`startOffset: 3, endOffset: 50`，即定位到某块文本的第 3 到第 50 个字符，配合 `quotedText` 可精确回显原文片段。

**写明这一点，是为了让后续 agent 不要再把"加偏移量"当成待办**：块级定位 + 字符级偏移的"三元组"（原件哈希 / 块 ID / 字符区间）**已经存在**，工作量应投到展示与验证上，而不是重做定位结构。

## 10. 给后续 agent 的决策清单

1. **守住两条机制差异**并在演示中显式展示拒绝路径：规则版本门禁（§2.1）、Finding 证据约束（§2.2）。
2. **补齐"审查尺度"**（严格 / 中立 / 宽松）：一份预设参数 + 复用草稿链路，成本接近零（§3）。
3. **docx 修订回写**用 `docx-redline-js`（JS 栈优先）或 `docx-revisions`；**不要用 `docxtemplater` 做修订**（§4）。
4. **插件形态选 WPS 加载项**，部署走 `wpsjs publish`；**弃用 `jsplugins.xml`**（12.1.0.16910 起受限）；不用 Office.js 做修订（§5）。
5. **验证集从 CUAD 切到 ProvBench/ProvData**，用好其 663 条法条库（§6）。
6. **对外口径**：LawGeex 数字必须带三条限定，或改用 ContractEval（2025）（§7）。
7. **跨条款一致性**作为压轴演示点，对照 ACE/COMPACT 的 34–57%（§8）。
8. **别重做证据定位**：`DOCUMENT_SPAN` 已带 `startOffset` / `endOffset`（§9）。
